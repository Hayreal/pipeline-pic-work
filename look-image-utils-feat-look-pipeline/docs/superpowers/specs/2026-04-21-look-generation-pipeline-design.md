# 商品 Look 生成流水线 — 设计说明

**日期**：2026-04-21  
**状态**：已定稿待实现评审  
**范围**：基于 Gemini 多模态理解 + Nano Banana（原生图生/编辑）的半自动流水线；与仓库内 `docs/图像理解官方文档.md`、`docs/Nano Banana官方文档.md` 能力对齐。

---

## 1. 目标与成功标准

### 1.1 输入（六类角色）

| 角色 | 说明 |
|------|------|
| SKU 平铺图 | 服装结构、版型、配色主依据 |
| SKU 面料特写 | 纹理、织法、微观细节 |
| 模特脸部特写 | 人物身份与肤质锚点 |
| Look 参考图 | 影调、镜头语言、场景气质主依据 |
| 动作姿态参考 | 体态与构图；**允许与某张 Look 参考图为同一文件**（共用路径） |
| 产品 Logo 特写 | Logo 几何、色彩与清晰度锚点 |

当「姿态」与「Look」共用时：在结构化 JSON 中显式标记 `pose_ref_source: "shared_with_look"`（或等价字段），Brief 编译器在 2a 阶段仍按 **Look（风格）** 与 **姿态（身体）** 两个语义块分别生成指令，避免模型混淆主次。

### 1.2 输出

- 最终交付：**4K 商品 Look 图**（具体像素以选用模型/API 实际支持为准；若单次调用无法直达 4K，则在设计中保留「链式：先结构再放大或二次生成」策略，见 3.2）。

### 1.3 一致性要求（人工闸门间可验证）

- **商品**：结构以平铺为主，纹理以面料特写为辅；**Logo 与特写一致**，允许在局部精修轮补强。
- **人物**：与脸部特写为同一人气质；肤质与皮肤细节尽量延续；姿态以姿态参考为主，仅允许 JSON 中声明的微调范围。
- **风格**：与所选 Look 参考一致；姿态参考不得压过 Look 的风格主导权。

### 1.4 运行模式

- **半自动（B）**：在「结构化 JSON → 2a 结构稿 → 2b 终稿 → 局部编辑」之间设置人工闸门；技术故障可自动重试，审美不通过走改参而非盲重试。

## 2. 约束与假设

### 2.1 传输与体积

- **不使用 File API**：所有图像以 **inline 字节** 随 `generate_content` 提交。
- **输入分辨率**：进入模型前统一预处理，**长边 ≤ 2048 px**（「2K」口径），并记录原始尺寸与缩放参数至血缘。
- 需监控 **单次请求总大小**（含文本与多图）不超过官方限制；可通过 JPEG/WebP 质量与长边上限组合保证稳定。

### 2.2 模型与 SDK

- 与现有 `main.py` 一致：使用 `google.genai` 的 `Client`；理解、2a、2b、编辑可为 **不同模型名配置**（例如草图用 Flash 系、终稿用 Pro 系），由配置项切换，本设计不绑定单一模型字符串。

### 2.3 测试数据

- 仓库 `tests/` 已备样例：**Look 图库**（`tests/Look参考图/look/`）、**SKU/面料**（`tests/SKU面料素材/` 及子目录 `面料与logo裁图/`）、**模特脸部特写**（`tests/模特脸部特写/`）。**Logo 特写图为可选**：夹具中可省略 `logo_detail` 字段，此时 manifest 中 `logo_detail.skipped=true`，流水线不得把面料图当作 Logo 参考。
- **夹具**：使用 `tests/fixtures/sample_run.json`（或同义路径）描述一次 run 的六类路径；**姿态可与 Look 指向同一路径**。

## 3. 架构

### 3.1 三层与闸门

1. **理解层**：六图（经预处理）→ 多模态理解 → **版本化 JSON**（含事实/推断/冲突/优先级）。**闸门 A**：人工审阅 `look_spec_approved.json`。
2. **分步生成层**  
   - **2a 结构稿**：非最终分辨率或非 4K，强调构图、身份、服装结构、Look 气质；附件集 **刻意精简**（默认：Look、姿态、脸、平铺；面料与 Logo 以 JSON 为主、图为辅）。**闸门 B**。  
   - **2b 终稿**：以 2a 输出为主图，**锁构图与身份**，提升细节与分辨率至 4K；此时再挂载面料特写、Logo 特写等。**闸门 C**（可选）。
3. **局部精修层**：图+文编辑，针对 Logo 与关键面料区域；可多轮。**闸门 D**（逐轮或批量）。

### 3.2 逻辑组件

| 组件 | 职责 |
|------|------|
| 输入规范化 | 齐套校验、缩放至长边≤2048、manifest 与 hash |
| Schema + 校验器 | JSON 版本、必填项、枚举、闸门前后校验 |
| 理解编排器 | 组装多图与指令，产出 `look_spec_vN.json` |
| Brief 编译器 | 将已批准 JSON 编译为 2a / 2b / 编辑 的文本块 + 附件列表 |
| 生成编排器 | 顺序调用 2a → 2b，分离文本与图像部件 |
| 编辑编排器 | 链式传入上一轮图像做局部修补 |
| 产物与血缘 | 每步输入快照、spec、brief 摘要、输出图、模型 id、时间戳 |

### 3.3 与现有代码关系

`main.py` 演进为同一 `Client` 下多条调用路径，差异在 `contents` 组装、模型选择与闸门间人工文件（如已批准的 spec）。

## 4. 数据流与产物（目录级约定）

以下为逻辑约定，实现时可映射为 `runs/<run_id>/` 等结构。

| 步骤 | 输入 | 输出 |
|------|------|------|
| 0 输入包 | 六路径 + 元数据 | `input_manifest.json`、预处理后的 inline 用图副本 |
| 闸门 A | 六图 + 抽取模板 | `look_spec_vN.json` → 人工 → `look_spec_approved.json` |
| 闸门 B | approved spec → Brief 2a | `brief_2a.txt`（摘要）、`draft_2a.png` |
| 闸门 C | draft_2a + Brief 2b | `brief_2b.txt`、`look_final_4k.png`（名称表示目标；若 API 分步则保留中间文件） |
| 闸门 D | 当前最佳图 + 编辑 brief | `look_patch_vM.png` 等 |

**血缘**：每步记录原始路径、缩放参数、模型名、关键 prompt 摘要（非必须全文），便于复盘。

## 5. 错误处理与重试

- **输入错误**（缺图、超大）：阻断并写入 manifest 原因。  
- **API 可恢复错误**（429、5xx、超时）：指数退避重试至配置上限；记录最后请求上下文。  
- **解析失败**（无图、非法 JSON）：保留 raw 输出；理解步骤可有限次重试；冲突字段过多时停止自动重试，转人工。  
- **安全拒答**：记录说明，不自动无限重试。  
- **闸门不通过**：新版本 spec/brief，**不覆盖**已批准产物；使用版本号或子目录隔离。

## 6. 测试与验收

### 6.1 夹具

- `tests/fixtures/sample_run.json`：列出 `look_ref`、`sku_flat`、`fabric_detail`、`face`、`pose_ref`；**`logo_detail` 可选**（省略表示无单独 Logo 图）。**允许 `pose_ref` 与 `look_ref` 相同路径**。  
- 若 `fabric_detail` 与平铺共用同一文件，schema 仍保留独立字段，便于后续拆图。

### 6.2 建议用例

- **快乐路径**：六角色路径有效 → 过 A→B→C→（可选 D）→ 产物齐全。  
- **闸门回退**：矛盾输入期望在 B 或 A 失败，且不覆盖已批准中间件。

### 6.3 自动化（可选）

- 输出文件存在性、JSON schema、manifest 哈希；若 API 稳定返回固定尺寸则断言分辨率。  
- **主观一致性**首版依赖人工评分表（Logo、面料、人脸、Look、穿模）。

## 7. 非目标（本版不做）

- 全自动批量无人值守。  
- File API 与大文件托管。  
- 侵权或无权素材的合规审查逻辑（使用者需自行保证权利）。
